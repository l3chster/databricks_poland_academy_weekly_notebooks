# PySpark Pipelines: Declarative vs Classic (Imperative)

| What are we comparing? | Declarative approach | Classic / Imperative approach |
| :--- | :--- | :--- |
| **What is it about?** | You describe **what** should happen to the data, for example through DataFrame operations or SQL. Spark builds an execution plan and decides how to execute it. | You organize the code as a **sequence of steps and instructions**, often splitting the logic into functions, variables, and control-flow statements. |
| **Typical PySpark APIs** | DataFrame API, Spark SQL, and pipeline-oriented solutions that use declarative transformation definitions. | Regular Python code controlling the processing, custom functions transforming DataFrames, loops, conditions, and lower-level APIs such as RDDs. |
| **Execution optimization** | Spark can analyze the complete operation plan and apply optimizations, for example through Catalyst and execution-level optimizations. | Spark optimizations are still available when DataFrame APIs are used inside the steps, but additional Python-side logic can limit what the Spark engine can optimize. |
| **Pipeline organization** | The pipeline is a description of transformations and dependencies between stages. It is easier to see the data flow as a whole. | The pipeline is usually represented by code: one function calls another, the result of one step is passed to the next, and so on. |
| **Making changes** | Changes often involve adding, removing, or modifying transformations in the plan. | Changes may require modifying the order of function calls, variables, and dependencies between steps. |
| **Testing** | Individual transformations can be tested independently, and the declarative description makes it easier to verify the expected data flow. | Much of the logic may live in Python functions, which provides flexibility but requires deliberate decomposition into testable components. |
| **Production deployment** | A declarative style does not automatically make deployment simple. Deployment also depends on packaging, dependency management, configuration, and orchestration. | Deployment requires shipping the application code and its dependencies. With well-structured code, this does not necessarily have to be difficult. |
| **Flexibility** | Works particularly well when processing can be expressed as a set of operations on data. | Provides more freedom for control-flow logic such as `if`, `for`, error handling, calls to external systems, or dynamically constructed processes. |
| **Typical use cases** | ETL/ELT, DataFrame transformations, SQL queries, aggregations, joins, filtering, and other operations that Spark can analyze and optimize. | Process orchestration, application logic, dynamic pipelines, integrations with external systems, and situations requiring greater control over execution flow. |
